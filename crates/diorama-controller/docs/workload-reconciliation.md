# Workload and Garbage-Collection Reconciliation

## 1. Overview
The diorama controller manager (`diorama-controller`) is responsible for reconciling core Kubernetes workload resources and garbage collecting dependent objects when owners are deleted. This implements the requirements of Epic E12 ([#12](https://github.com/geoffsee/diorama/issues/12)), Issue [#67](https://github.com/geoffsee/diorama/issues/67) (`[E12.02] Verify workload and garbage-collection reconciliation`).

The workload reconcilers implement standard Kubernetes reconciliation semantics:
- **Deployments** produce and scale child **ReplicaSets**.
- **ReplicaSets** produce and scale child **Pods** in `Pending` phase.
- **StatefulSets** produce ordered ordinal child **Pods** (`<name>-0`, `<name>-1`, etc.).
- **DaemonSets** produce node-level child **Pods**.
- **Jobs** produce child **Pods** with required batch labels (`job-name`, `batch.kubernetes.io/job-name`).
- **CronJobs** produce scheduled child **Jobs**, which subsequently produce child **Pods**.
- **GarbageCollector** cascades deletions of orphaned child resources when parent owners are deleted based on `metadata.ownerReferences`.

## 2. Decoupling from Scheduler and Container Execution
In conformance with Kubernetes architectural design and Issue #67 acceptance criteria:
- **Scheduler Decoupling**: Reconciled child Pods are created with status phase `Pending` and without `spec.nodeName` assignments. Controllers do not require a running scheduler (`kube-scheduler`) to verify object reconciliation. Production binding is performed by upstream kube-scheduler v1.35.7; actual qualification is recorded in `tests/multinode/QUALIFICATION.md`.
- **Runtime Execution Decoupling**: Pod container execution follow-through (CRI runtime, containerd, cgroups, namespace isolation) is intentionally identified and tracked for Epic E28 (`[E28] Live workload execution and container lifecycle`). Controller reconciliation strictly verifies declarative API object creation, owner reference graphs, and state convergence.

## 3. Child Resource Generation and Owner References
Every child resource generated by a controller includes an entry in `metadata.ownerReferences` identifying its managing parent:
```json
{
  "apiVersion": "apps/v1",
  "kind": "Deployment",
  "name": "nginx-deployment",
  "uid": "uid-deployments-nginx-deployment-1",
  "controller": true,
  "blockOwnerDeletion": true
}
```

### Deterministic Naming and Idempotence
To guarantee that repeated reconciliation passes, controller restarts, and retry attempts converge without creating duplicate child resources:
1. **Deterministic Child Names**: Child objects use deterministic names derived from the parent name and ordinal/role:
   - Deployment -> `{deployment_name}-rs`
   - ReplicaSet -> `{replicaset_name}-{index}`
   - StatefulSet -> `{statefulset_name}-{ordinal}`
   - DaemonSet -> `{daemonset_name}-node`
   - CronJob -> `{cronjob_name}-scheduled`
   - Job -> `{job_name}-{index}`
2. **Pre-Creation Existence Check**: Reconcilers check for existing objects matching the deterministic name before issuing create requests.
3. **Owner Reference Validation**: Reconcilers inspect existing resources in the namespace to associate only those matching owner references (matching `kind` plus `uid` or `name`).

## 4. Garbage Collection and Cascading Deletion
The `GarbageCollector` reconciler inspects all dependents (Pods, Jobs, ReplicaSets) in a namespace.
An object is eligible for garbage collection if it possesses one or more `metadata.ownerReferences`, and **all** referenced parent owners no longer exist in the API datastore.

### Multi-Pass Cascading Algorithm
Because owner graphs can be multi-tiered (e.g. `Deployment` -> `ReplicaSet` -> `Pod` or `CronJob` -> `Job` -> `Pod`), the garbage collector executes successive passes until no further deletions occur:
1. **Pass 1**: Deleting a `Deployment` leaves child `ReplicaSet` orphaned. The garbage collector detects that the parent `Deployment` does not exist and deletes the `ReplicaSet`.
2. **Pass 2**: With the `ReplicaSet` deleted, the child `Pod`s are now orphaned. The garbage collector detects that the parent `ReplicaSet` does not exist and deletes the child `Pod`s.
3. **Pass 3**: Zero objects are eligible; cascading deletion is converged.

## 5. Verification Matrix

| Controller | Primary Managed Child | Owner Reference Kind | Scaling Convergence | Cascading GC Verified |
|------------|-----------------------|----------------------|---------------------|------------------------|
| Deployment | ReplicaSet            | Deployment           | Yes                 | Yes (Deployment -> RS -> Pod) |
| ReplicaSet | Pod                   | ReplicaSet           | Yes                 | Yes (ReplicaSet -> Pod) |
| StatefulSet| Pod (Ordinal)         | StatefulSet          | Yes (reverse ordinal order) | Yes (StatefulSet -> Pods) |
| DaemonSet  | Pod (Node)            | DaemonSet            | Yes                 | Yes (DaemonSet -> Pod) |
| Job        | Pod (Batch)           | Job                  | Yes                 | Yes (Job -> Pods) |
| CronJob    | Job                   | CronJob              | Yes                 | Yes (CronJob -> Job -> Pods) |
| GC         | Pod, Job, ReplicaSet  | Deployment/RS/SS/DS/Job/CronJob | N/A     | Converges to 0 orphans |
